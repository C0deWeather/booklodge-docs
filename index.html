Frontend integration guide

Everything needed to take a customer from a search to a confirmed hotel reservation: the six steps, every endpoint, and what to do when the provider says no.

Read these two rules first

Never send payment data to POST /api/bookings. It accepts prebookId, holder and guests — nothing else. No transactionId, and no paymentSuccessful: true. The server books using the prebook pair it stored, so a flag from the browser can never authorise a booking.

When a response carries ambiguous: true, stop and do not retry. That flag means the hotel provider may have completed the booking even though the call failed. Retrying can produce a second reservation. Show "we're checking your booking" and point the customer at their booking list.

Talking to the API

All endpoints live under /api. Requests and responses are JSON; send Content-Type: application/json on anything with a body. In development the server listens on port 5000, so the base URL is http://localhost:5000/api. Ask the team for the deployed host.

CORS is locked to one origin. Requests from anywhere else are refused with 403 Not allowed by CORS, so run the frontend on the origin the backend was configured with (FRONTEND_URL, http://localhost:3000 by default).

Every response has the same envelope

// success
{ "success": true, "message": "Hotels retrieved successfully", "data": { } }

// failure
{ "success": false, "message": "No pending prebook for this booking", "data": null }

Branch on success, read message when you need something to show a person, and take the payload from data. A failure that came from the hotel provider puts a provider object in data instead of null — see Errors.

The booking flow

Six steps. Steps 1–3 are ordinary reads, step 4 starts a reservation hold, step 5 is yours, and step 6 is a request the server will only honour once payment has actually settled.

  • frontend you drive this
  • backend the API handles it
  1. 01

    Find the place

    frontend

    Autocomplete. Each result carries the placeId that step 2 needs.

    GET /api/locations/search?query=Paris

  2. 02

    Search hotels

    frontend

    Give the placeId, the dates and the occupancy. You get hotels back, each with its cheapest available rate for those dates.

    POST /api/hotels/search

  3. 03

    Open a hotel and pick a room

    frontend

    Every rate here has an offerId. That string is the only handle the provider accepts, so carry it into step 4 and don't invent or modify one.

    POST /api/hotels/:hotelId/details

  4. 04

    Prebook — hold the room and the price

    frontend calls it backend owns the state

    The provider re-checks availability and re-prices the room, then returns the three things the rest of the flow depends on: prebookId, transactionId and secretKey. The server also records this as a pending booking attempt and hands back a clientReference.

    The customer must already be logged in. This endpoint needs a token, and step 6 only works for the same account. There is no guest checkout.

    POST /api/bookings/prebook  auth

  5. 05

    Take the payment

    frontend only

    Hand secretKey to LiteAPI's Payment SDK and let the customer pay. No backend call, and no Stripe account of our own — the SDK talks to LiteAPI's Stripe integration directly.

    Treat secretKey as a live credential for this one payment: keep it in memory for the session, never in localStorage, never in a URL or analytics event, and never in a log. The server deliberately does not store it, so if you lose it, prebook again.

    Follow LiteAPI's docs for the SDK itself

    The SDK's own initialisation and its success callback are LiteAPI's surface, not ours — use their documentation for the exact wiring. Two things about it are ours to flag: the SDK's publicKey is the literal "sandbox" or "live" rather than one of our keys, and after a successful payment it returns the customer to the returnURL you configured with LiteAPI. Treat arriving back at that URL as "payment likely done", then call step 6 and let the answer be the truth.

  6. 06

    Book it

    frontend calls it server decides

    Send the prebookId and the guest details. The server books with the stored payment pair, so this call succeeds only if the payment behind that pair actually settled. This is the payment gate: the provider, not the browser, is what establishes that money moved.

    A 201 means the reservation exists — show the confirmation. Anything else, read the error before deciding what to tell the customer.

    POST /api/bookings  auth

Holds expire — don't prebook speculatively

A prebook reserves inventory. The server expires the attempt 48 hours after it is created, and the provider releases an unpaid hold after one to two business days. Prebook when the customer is ready to pay, not while they browse, and don't loop over offers. If a customer abandons checkout, nothing needs cleaning up — the hold lapses on its own.

Auth

One token, sent as a Bearer header on everything that needs it. The payload is { userId, role } and the lifetime comes from JWT_EXPIRES_IN (an hour in development), so handle expiry as normal operation rather than an error state.

Authorization: Bearer <token>

The three ways a token can be refused are worth distinguishing in the UI. All three are 401:

Whenmessage
No header at allNo token provided
Header present but not Bearer <token>Invalid authorization format
Expired or tampered withInvalid or expired token
Register and login return the user id differently

Register gives you the stored document, so the id is data.user._id. Login gives you a trimmed object, so the id is data.user.id. Both work, but the key differs — persist the login one and don't assume the other.

Both auth routes are rate limited, and the limits count failures rather than requests:

RouteLimitOn exceeding
POST /api/auth/login5 failed attempts per 15 min, per IP + email429 Too many failed login attempts. Please try again in 15 minutes.
POST /api/auth/register5 per hour, per IP429 Too many requests. Please try again in an hour.

Successful logins don't count towards the limit, so a working sign-in flow never locks itself out. Show the message on a 429 — it already says how long to wait.

Endpoints

Request bodies are validated with a strict schema: unknown keys are dropped, and a missing or wrongly-typed field fails with 400 before anything reaches the provider. Dates are ISO YYYY-MM-DD, and prices are numbers in the currency you asked for.

Stay criteria

Steps 2 and 3 share one object. Step 3 is identical minus placeId.

  "currency": "USD",
  "guestNationality": "US"

checkin / checkoutISO dates. Checkout must be after checkin.

Failures

  • 401 — no valid token. Send the customer through login first.
  • 502 with provider code 2001 — the room sold out or the price moved between the search and now. Go back to step 3 and show the new price.
  • 502 with data.provider: null — the connection dropped and no answer came back. Nothing is known about whether a hold was created, and the server does not retry a prebook on its own. Calling it again is fine: a hold that did get made lapses by itself, so the worst case is a second hold nobody pays for.
  • 400 — missing or wrong-typed offerId.

GET /api/bookings/my-bookings auth

Query

page (default 1) and limit (default 10, maximum 50). Anything outside that is a 400.

Response 200

{
  "success": true,
  "message": "Bookings retrieved successfully",
  "data": { "bookings": [ /* … */ ], "total": 3, "page": 1, "limit": 10 }
}
This list is a summary

List items omit userId, payment and liteApi, so there's no provider booking id or transaction id here. Fetch the single booking if you need the full record. Build pagination from total, not from bookings.length.

GET /api/bookings/:bookingId auth

One booking, in full — including payment and liteApi.bookingId. The id must be a 24-character hex string, so validate it before you send it rather than letting a placeholder through: a malformed id is a 400.

A booking that exists but belongs to someone else reads as 404 Booking not found, not 403. Don't build UI that distinguishes them — from the client's side they're the same thing.

GET /api/bookings/:bookingId/confirmation auth

A deliberately small endpoint for polling one thing: { "status": "CONFIRMED" }. Useful after an ambiguous result, or on a confirmation screen that reloads.

PUT /api/bookings/:bookingId auth

Cancels through the provider. No request body.

Response 200

{
  "success": true,
  "message": "Booking cancelled successfully",
  "data": {
    "bookingId": "…",
    "status": "CANCELLED",
    "cancellationFee": 40.23,
    "refundAmount": 362.06,
    "currency": "EUR"
  }
}
ResponseMeaning
400The booking isn't CONFIRMED, so it can't be cancelled — already cancelled, or never completed.
403Not this customer's booking and not an admin.
502The provider refused or failed. The local status is unchanged, so the booking is still live — check the provider code before telling anyone it's cancelled.

The fee and refund come from the provider's cancellation policy. They can be null, and they arrive in the booking's currency — show it. Since cancellation is final and costs money, confirm with the customer first, and read the fee back to them before you call this.

GET /api/health no auth

Returns 200 with { "message": "OK" } whenever the server process is up. It's a liveness check for deployment, not a status page — it doesn't tell you anything about the database or the provider.

Statuses

A booking's status is what you render. In practice you'll see two values, because a record is only written once the provider has confirmed the reservation.

statusWhat to show
CONFIRMEDThe reservation exists. Show the confirmation, the reference and the stay details.
CANCELLEDCancelled through the provider. Show what was refunded if you have it.

The schema also allows PENDING_PAYMENT, BOOKING_PROCESSING, PAYMENT_FAILED and BOOKING_FAILED. Handle them defensively with a neutral "processing" state rather than a specific screen, but don't build a checkout flow that depends on seeing them — the current API doesn't produce them.

Payment and booking are separate states

A payment that succeeded is not a booking that succeeded. Until step 6 returns 201, there is no reservation, whatever the payment SDK showed. The server keeps the attempt's own state separately, and an ambiguous outcome is recorded for investigation rather than discarded — which is why a booking can turn up in the customer's list after a call that looked like a failure.

Errors

The HTTP status tells you who is at fault. The provider block, when present, tells you why — and ambiguous tells you whether it's safe to try again.

{
  "success": false,
  "message": "Booking failed",
  "data": {
    "provider": { "code": 2014, "description": "booking incomplete" },
    "ambiguous": true
  }
}
StatusMeaningWhat to do
400The request is malformed — a missing field, a bad date, an id that isn't 24 hex characters.Fix the request. This is a bug on our side of the wire, so the message is worth logging.
401No valid token.Send them to log in and retry the call.
403Authenticated, but not allowed — a cancelled booking, or someone else's record.Don't retry. Hide the action instead.
404Not found, or not theirs. Also used when the provider itself says 404.Show an empty state.
409The request conflicts with current state — most often a prebook that was already consumed.Refresh state rather than retrying the same call.
429Rate limited; only login and register are limited.Show the message and wait. It states the interval.
502The provider failed, or its response didn't make sense. data.provider carries the detail, or null if no answer arrived.Read the code below before choosing.
500Something broke on the server. The message is always Internal server error on purpose — details stay in the server log.Show a generic failure. Report it with the time and the endpoint.

Provider codes worth handling

These are the provider's own codes, not HTTP statuses. Match on code, never on the status alone, and prefer description when you need user-facing text.

codeMeaningSafe to retry?
2001No availability, or the price moved since the search.Not this call — re-run the search or the room list and show the new price.
2013 / 2014 / 5000Booking failed, incomplete, or the provider couldn't process it. ambiguousNo. The booking may exist. Check the booking list.
4002 / 4003Missing, invalid or unacceptable field — including the payment method.No. Nothing was booked; the customer starts again.
4005This reference was already used.No. Look for the existing booking.
4290 / 4291The provider rate-limited us.Yes — but only after a pause. The server already retried a few times with backoff before you saw this.
The server retries reads, never bookings

Searches, hotel details and location lookups are retried inside the API: rate limits get a backoff, and a dropped connection to a read is attempted again. Booking and cancelling are never retried automatically, because the provider may have completed the work before the connection failed. If you see a 502 from a booking call, the server made exactly one attempt — which is precisely why its outcome can be unknown and why you must not paper over it with a retry of your own.

Checklist before you ship

  • Token attached as Bearer on every /api/bookings call, and a 401 sends the customer through login.
  • Login happens before prebook — there's no guest path, and the token's owner is who the booking belongs to.
  • Login's user id read from data.user.id; register's from data.user._id.
  • secretKey never stored, logged, or put in a URL, and used for one payment only.
  • Nothing derived from the client is trusted as payment proof — no paymentSuccessful flag is ever sent.
  • Prices shown come from the API response, never from a client-side calculation, and the post-prebook price replaces the search price once you have it.
  • offerId passed through untouched from the details response.
  • ambiguous: true, 409, and a 502 with provider: null all lead to "we're checking", never to an automatic retry.
  • Dates formatted as YYYY-MM-DD; children sent as [] when empty.
  • Booking list built from total, with limit at or below 50.
  • Cancellation confirms with the customer and reads back the fee before calling, and treats 502 as "still booked".
  • Frontend served from the configured FRONTEND_URL origin, or CORS will refuse every call.

Questions about a response shape or an unexpected provider code: send the endpoint, the time, and the message and data.provider.code from the response. The server logs the full provider error alongside it, which is usually enough to say exactly what the provider objected to.
